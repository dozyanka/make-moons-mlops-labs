## 1. Методика параллельного бенчмарка

`joblib.Parallel(prefer=threads)`; доступные логические ядра определяются `os.cpu_count()`; измерения включают 2 прогревочных запроса на конфигурацию, затем независимые повторы.
Размер пакета 6000; повторов 4; режим: TestClient в одном процессе. p50/p95/p99 по повторам приведены для одного пакетного HTTP-вызова.

| 1 | 209957.88 | 28.59 | 28.39 / 29.42 / 29.52 |
| 2 | 201012.00 | 29.85 | 29.86 / 30.15 / 30.19 |
| 4 | 198315.68 | 30.26 | 30.26 / 30.72 / 30.77 |
| 8 | 153852.95 | 50.97 | 32.50 / 96.19 / 105.08 |

Максимальная производительность достигнута при одном исполнителе. Увеличение числа исполнителей до 2, 4 и 8 не обеспечило ускорения на выбранной нагрузке из-за расходов параллельной обработки.

## 2. Оконное наблюдение Evidently и PSI / KS / CSI

Окно: 1000 наблюдений; шаг: 500; окон на сценарий: 8. Новый блок поступает из генератора ЛР5, окно хранится в `deque(maxlen=window_size)` без накопления всего потока.
Дрейф вводится на окне 4 (отсчёт с нуля); порог max(PSI(x1), PSI(x2)) > 0.2, или CSI(вероятность) > 0.15; срок обнаружения ≤ 2 окон после начала дрейфа.
Evidently `DataDriftPreset()` рассчитывается на каждом окне по `x1`, `x2`, `probability`.

| clean | — | — | 0 | PASS |
| mean_shift | 4 | 0 | 0 | PASS |

## 3. Негативный контроль исполнителя

Отказ joblib воспроизводится инъекцией исключения в `Parallel`: сервис переходит к последовательному расчёту, не теряя ответ.
Результат: `{"fault": "simulated joblib Parallel exception", "batch_status": 200, "health_during_fault": 200, "predictions": 2, "fallback_counter_delta": 1, "pass": true}`.

Прогон использует фиксированные seed из конфигурации; при повторе совпадают значения генератора и метрики окон в пределах численной точности окружения. Производительность зависит от загруженности CPU.
