# ЛР №4 — валидатор (вариант 09 `make_moons`)

Самостоятельный запуск для преподавателя на **Windows 10/11**.

## Цель

Классификатор из ЛР №2 уже предсказывает принадлежность точки к одной из двух лун.
В этой работе строится отдельный **валидатор применимости предсказания**, который
может отказать на нетипичном входе или при слишком низкой уверенности модели.
Сравниваются оценки статистик для полного train и потокового чтения 24 чанков.

## Запуск с нуля после скачивания GitHub-репозитория

1. Установить Python **3.11+** с поддержкой `venv`; интернет нужен только для первичной установки пакетов.
2. Распаковать **весь репозиторий** (сохранённые CSV и модель ЛР2 уже включены).
3. Дважды щёлкнуть `LAB4\RUN_LAB4.cmd` или открыть PowerShell в корне репозитория:

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File .\LAB4\RUN_LAB4.ps1
   ```

4. Скрипт создаёт `.venv`, устанавливает `.[tracking,test]`, **не перегенерирует**
   данные и **не переобучает** ЛР1–3. Он выполняет `scripts/run_lab4.py`
   (2 исходных + **2 независимых повторных** прогона), затем pytest-проверки
   всех компонентов ЛР4 и сохраняет `reports/LAB4/pytest_coverage.log` +
   `coverage_details.json`.
5. Открыть `reports/LAB4/lab4_report.md`, `validator_metrics.csv`,
   `validator_negative.log`, `negative_summary.json`, `comparison.json`,
   `reproducibility.json`, `repeat_verification.json`, `source_manifest.json`.
6. Быстрая демонстрация сохранённых весов и отказов:

   ```powershell
   .\.venv\Scripts\python.exe .\defense_demo\lab4_demo.py
   ```

7. Для просмотра MLflow прогонов дважды щёлкнуть `LAB4\OPEN_MLFLOW_UI.cmd`
   (он учитывает настройку файлового хранилища в MLflow 3.16+). Либо из корня
   репозитория в PowerShell:

   ```powershell
   $env:MLFLOW_ALLOW_FILE_STORE = "true"
   .\.venv\Scripts\python.exe -m mlflow ui --backend-store-uri .\mlruns --port 5000
   ```

   Открыть `http://127.0.0.1:5000` → **Model training** → `lab4_validator`.
   Ожидаются `lab4_full`, `lab4_chunks`, `lab4_full_repeat`,
   `lab4_chunks_repeat`, все со статусом **Finished**. Это локальный интерфейс,
   а не публичный сайт и не требование использовать именно порт 5000.

**MLflow 3.16+:** файловый бэкенд `mlruns/` находится в режиме поддержки
совместимости. Письменное задание требует хранить прогоны именно в локальном
`mlruns/`, поэтому запуск ЛР4 явно устанавливает `MLFLOW_ALLOW_FILE_STORE=true`.
Это не удаляет и не мигрирует старые эксперименты и действует лишь для процесса
запуска. Отдельный лаунчер MLflow UI включает тот же флаг.

**Администратор не требуется.** Нельзя запускать общий `RUN_ME_WINDOWS.ps1` для одной ЛР4:
он запускает другие лабораторные и может перезаписать их результаты.

## Настройки и алгоритм

- `configs/lab4.json` — схема Pydantic `Lab4Config` находится в `src/moons_lab/config.py`.
- Обучение только по `data/processed/train.csv` / `data/chunks/`, без test.
- Калибровка только по `data/processed/validation.csv`: целевой уровень ложных отказов 3%.
- Финальная проверка на `data/processed/test.csv`: допускается не более 5% ложных отказов.
- Заранее объявленная полнота отказа для чужеродных данных: не ниже 90%.
- Две числовые OOD-группы: сдвиг среднего, крайние выбросы.
- Чужие категории отвергаются схемой, а подмена меток контролируется **только если
  заявленная метка предоставлена**, иначе переворот не наблюдаем по входным признакам.
- `validator_negative.log` записывает *каждый* тестовый чужеродный вход и фактический
  исход, включая ошибки; не только удачно отвергнутые примеры. В
  `negative_summary.json` отдельно указано, сколько flip-меток ошибочно приняли.
- Строгие типы: `"0.5"` (строка), булевы значения, `null`, `nan`, `inf` и
  неизвестные категории отклоняются до вызова рабочей модели.
- Два режима повторно обучаются на тех же входах; SHA-256 сохранённого NPZ,
  решения и ключевые метрики сравниваются в `repeat_verification.json`.
  Новые MLflow Run ID создаются автоматически. Это не сравнение времени до мс.

Все числа и критерии формируются скриптом, а не подставляются в отчёт вручную.
`mlruns/` исключается из Git: на другом ПК скрипт автоматически создаёт новые прогоны
с новыми Run IDs и переписывает отчёт под них. Для сдачи в ЭЮ также потребуются
скринкаст, рецензия БЯМ и критический комментарий — их выполняет студент.

## Проверка изменения исходных файлов

Оригинальные CSV и `.joblib` из ЛР1–3 **не перезаписываются**.
В отчёте указаны их SHA-256. Если тест обнаружит неправильные данные или зависимость,
он завершится с ошибкой, а не выдаст фиктивный успех.

## Подготовка публикации и защиты

- `LAB4/PATCH_03_APPLY.md` — установка последнего патча.
- `LAB4/GIT_AND_REPORT.md` — двухкоммитный процесс, предотвращающий устаревший
  SHA кода в отчёте; **никакой Git push патч не выполняет**.
- `LAB4/COVERAGE_SCOPE.md` — что измеряется `pytest-cov`, какие общие ветви
  относятся к остальным работам и почему суммарное покрытие не равно покрытию
  одного валидатора.

> **Windows / WinError 5 на pytest:** применять патч №04, см. `PATCH_04_APPLY.md`. Тесты используют отдельные временные директории, права администратора не нужны.


### Дополнительная проверка Windows/MLflow (патч №05)

При запуске через Windows PowerShell 5.1 файл `reports/LAB4/pytest_coverage.log`
теперь автоматически конвертируется в **UTF-8** для GitHub. Уже созданный лог
можно исправить **без повторного эксперимента**:

```powershell
& .\LAB4\NORMALIZE_COVERAGE_LOG.ps1
```

Если MLflow печатает `MissingConfigException` для старых каталогов `mlruns/2`
или `mlruns/3`, запустить **только чтение**:

```powershell
& .\LAB4\CHECK_MLFLOW_STORE.ps1
```

Скрипт не исправляет и не удаляет каталоги: они могут принадлежать прошлым
экспериментам. Сначала требуется изучить содержимое и сделать резервную копию.
Наличие таких предупреждений само по себе не отменяет `FINISHED` для валидных
прогонов ЛР4.

## Патч 06 — публикация и точные SHA-256

При проверке преподавателем GitHub-ветки `lab4` исходные 28 CSV должны иметь те же SHA-256, что и в `LAB4/data_integrity_baseline.json`. Это обеспечивается правилами `.gitattributes`: исходные CSV хранятся в Git **байт-в-байт**, без перевода CRLF в LF.

Для проверки без обучения: `python scripts/verify_lab4_data.py --check-git-index --check-published`.
Команда проверяет также, что `source_manifest.json` соответствует исходникам в коммите кода и что итоговый отчёт ссылается на этот коммит.

Публикацию запускают отдельно, см. `LAB4/GIT_AND_REPORT.md`.
